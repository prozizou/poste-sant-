# Audit et corrections du 29 octobre 2026

État : corrections dans le dépôt, sans déploiement ni modification des données
Firebase de production. Les résultats ci-dessous concernent le code exécuté
localement, avec une base simulée pour les essais transactionnels et navigateur.

## Calculs et écritures corrigés

| Cause | Correction |
| --- | --- |
| Même identifiant accepté avec un autre panier ou patient | Empreinte SHA-256 du contenu canonique, liée à l’utilisateur, à l’action et au village. Un contenu différent est refusé ; un rejeu exact retourne le résultat déjà enregistré. Les anciennes commandes sans empreinte exigent une vérification dans l’historique. |
| Nouvelle écriture après une réponse perdue ou une erreur d’affichage | Identifiant et commande originale conservés dans la session de l’onglet. Le formulaire modifié n’est pas envoyé tant que l’ancienne saisie reste ambiguë. Un bouton permet de vérifier cette saisie. Les créations ne sont acquittées qu’après remise à zéro du formulaire ; un refus de session après coupure ne supprime pas l’identifiant incertain. |
| Dépenses concurrentes fondées sur un solde affiché périmé | Solde recalculé sur l’état transactionnel serveur. La dépense, sa preuve d’idempotence et sa trace sont validées ensemble. Une opération qui aggraverait un solde négatif est refusée, y compris une annulation de recette déjà dépensée. |
| Ventes, ajustements et retraits utilisant différents mécanismes | Transaction RTDB sur le sous-arbre du village, commune à toutes les mutations métier. Le verrou à bail de 90 secondes est supprimé. En cas de conflit, les calculs sont repris sur le dernier état. |
| Quantité et journal écrits séparément | Création, modification, retrait de lot, ajustement, archivage et réapprovisionnement valident leurs données et leur historique dans le même commit. Un inventaire ouvert avant une vente est refusé si le stock attendu a changé. |
| Création de tickets contrôlée seulement dans le navigateur | Tarif recalculé au serveur, auteur issu de l’identité authentifiée, prix et montant remis validés. Compteur et ticket créés ensemble. Créations, modifications, annulations et restaurations passent par l’API. |
| Montants invalides devenant `NaN`, zéro ou des chaînes concaténées | Valeurs communes `domain-values.mjs` : FCFA entiers, positifs ou nuls selon le champ, bornés aux entiers sûrs. Les données financières incohérentes bloquent les calculs avec un message explicite. Les saisies décimales ne sont plus transformées silencieusement en un autre montant. |
| Dates absentes remplacées par aujourd’hui | Horodatage invalide conservé comme invalide et exclu des périodes, avec avertissement de qualité. Aucune date historique n’est inventée. Les dates civiles impossibles sont refusées. |
| Dates futures incluses dans les rapports | Bornes supérieures fermées sur l’instant de référence ; filtres personnalisés également limités à maintenant. Les dépenses nouvelles datées du jour ne sont pas placées artificiellement à midi si midi est encore futur. |
| Médicaments différents fusionnés par nom | Regroupement par `stock_key`. Pour les anciennes lignes sans identifiant, repli sur nom, dosage et forme lorsqu’ils sont disponibles ; aucune référence historique n’est inventée. |
| Annulations rattachées au jour de vente dans le résumé quotidien | Le résumé des annulations utilise `annule_ts`, sans attribuer arbitrairement à aujourd’hui une annulation dont la date manque. |

Les écritures directes du navigateur sur tickets, dépenses, quantités, prix,
lots, compteurs et journaux sont désormais interdites par les règles RTDB.
Seuls les champs d’image explicitement autorisés restent modifiables directement
par un administrateur actif du village sur un produit existant. Les API
revalident les droits indépendamment du rôle affiché dans l’interface.

## Autres protections déjà appliquées

- Service worker limité au cache des ressources publiques ; API et requêtes
  authentifiées sans cache et anciens caches supprimés à l’activation.
- Identifiants de snapshots non écrasables par les champs métier ; actions de
  facturation/annulation déléguées à une liste explicite de gestionnaires.
- Transactions sur les changements de droits et les échéances des villages.
- Demandes publiques atomiques, sans écrasement d’un dossier par un doublon.
- Validation JSON et limites de taille communes aux API ; réponses privées.
- Firebase Admin 13.10.0 compatible avec le chargeur CommonJS Vercel, Node 24,
  lockfiles et CI ; protections HTTP Vercel. Les valeurs partagées sont chargées
  avec `import()` avant les transactions synchrones.
  La dépendance transitive `uuid` est fixée à 11.1.1 : version CommonJS corrigée
  pour les appels `v4()` des bibliothèques Google, sans les anciennes versions
  signalées par l’audit de dépendances.

## Vérifications réalisées

- Maintien de l’écoute Firebase pendant les transactions pour empêcher un faux
  « Ticket introuvable » après éviction du cache d’une lecture ponctuelle.
  L’écoute est libérée après succès ou échec. Les erreurs de suppression restent
  visibles dans la fenêtre de confirmation.
- **85 tests Node réussis**, aucun échec ni test ignoré : démarrage des API et
  encaissements sans `require(ESM)` ; logique métier,
  collisions d’identifiants, reprises, concurrence avec nouvelles tentatives,
  solde insuffisant, rollback du journal, attribution du numéro de ticket,
  isolation des villages, valeurs et périodes, frontières HTTP et cache PWA.
- **8 scénarios Chromium réussis** : suppression administrateur de ticket et vente,
  corbeille, restitution du stock et refus financier visible ; erreur texte Vercel
  puis reprise avec la même commande ; réponse perdue puis formulaire modifié ;
  refus de session après une réponse perdue ; erreur après confirmation puis
  nouvelle saisie identique ; écran caisse ; écran dépenses avec décimales
  invalides ; ajustement depuis l’écran stock. Les vrais modules de l’application
  et les planificateurs transactionnels sont exécutés ; l’authentification,
  le transport RTDB et les intégrations externes sont simulés.
- Tests locaux des expressions d’autorisation du fichier de règles : refus
  des mutations financières directes et des écritures d’images inter-villages,
  anonymes, suspendues ou expirées. Ces tests ne remplacent pas Firebase Emulator.
- `npm ci`, `npm audit` racine (dépendances de développement incluses) et audit
  de `scripts/` réussis : aucune vulnérabilité connue signalée. Le dossier `functions/`, ancien relais
  remplacé, n’est pas remis en service.

## Activation et vérifications externes encore nécessaires

1. Déployer **ensemble** les nouvelles API, les interfaces et les règles RTDB.
   Les anciennes interfaces qui écrivent directement seront volontairement
   refusées par les nouvelles règles ; demander leur rechargement et vérifier
   l’activation du service worker. Une publication de l’environnement cloud
   de développement ne déploie pas l’application métier.
2. Exécuter les règles dans Firebase Emulator puis la recette sur une
   préproduction isolée. Java et les outils sont disponibles localement, mais le
   proxy cloud refuse le téléchargement officiel depuis
   `storage.googleapis.com` (CONNECT 403). L’ajout de ce domaine est enregistré
   dans le brouillon de configuration réseau ; il doit être enregistré/appliqué
   dans les paramètres cloud avant reprise de ce contrôle.
3. Examiner les avertissements sur les données historiques : les montants et
   dates invalides ne sont pas corrigés automatiquement sans source fiable.
   Aucun accès de production n’a été fourni dans cet environnement.
4. Vérifier les appels authentifiés Firebase réels, les en-têtes déployés,
   les sauvegardes/restaurations, l’impression et les notifications.

## Limites et autres travaux distincts

- La disponibilité physique des lots reste reconstruite selon le modèle FEFO
  historique. Une traçabilité réglementaire complète nécessite d’enregistrer
  les allocations réelles par lot lors de chaque délivrance et retour.
- Les bilans présentent les ventes actuellement actives à leur date métier.
  Cela ne remplace pas un grand livre comptable immuable des encaissements et
  remboursements à leurs dates de mouvement.
- Le relais FCM doit encore gérer les envois concurrents et les échecs partiels ;
  la demande publique peut bénéficier d’une protection anti-robot de l’hébergement.
- La transaction couvre le village pour garantir la cohérence des mutations.
  Sa charge dépend du volume historique, y compris l’audit : un test de charge
  et une politique d’archivage sont nécessaires avant un usage à grande échelle.
- Les commandes incertaines contiennent temporairement leur saisie dans la
  session de l’onglet et sont purgées à la déconnexion. Les vérifier avant de
  fermer la session ; consulter l’historique si l’onglet a été fermé.
